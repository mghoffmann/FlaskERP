Setting up a new Flask project

From an empty folder to a running app with a Dockerized PostgreSQL — the equivalent of dotnet new webapi, done by hand.

Step 1 — a virtual environment

Python installs packages globally by default. A virtual environment (venv) is a private, per-project copy of the Python interpreter and its package folder, so two projects can pin different versions of the same library. Everything in this project runs from .venv/:

# create it once (from the project root)
python -m venv .venv

# use it: either "activate" it in your shell...
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux/macOS

# ...or skip activation and call its executables directly:
.venv\Scripts\python.exe -m pytest
There is no direct .NET equivalent because you never needed one: MSBuild/NuGet resolve packages per-project automatically. Think of a venv as "the bin/ + packages/ folder, but you must create it and point your shell at it explicitly." Forgetting to activate the venv (and using a system Python instead) is the classic Python-newcomer error — the equivalent of building against the wrong SDK.

Step 2 — dependencies in requirements.txt

The Python analog of your .csproj <PackageReference> list is a flat text file. This project's, trimmed to the interesting lines:

flask~=3.1                 # the web framework
flask-sqlalchemy~=3.1      # glue: binds SQLAlchemy sessions to the Flask app/request
flask-migrate~=4.1         # glue: exposes Alembic as `flask db ...` commands
sqlalchemy~=2.0            # the ORM itself
alembic~=1.16              # schema migrations (EF Migrations equivalent)
psycopg[binary]~=3.2       # PostgreSQL driver (like Microsoft.Data.SqlClient)
gunicorn~=23.0             # production app server (the Kestrel role)
python-dotenv~=1.1         # loads .env files
pytest~=8.3                # test runner

pip install -r requirements.txt     # ≈ dotnet restore
~=3.1 is a "compatible release" pin — allows 3.1.x and 3.2, not 4.0. Same spirit as NuGet's floating versions, but the convention in Python is to commit the pins in the repo rather than a lock file (lock files exist — pip freeze, poetry, uv — but a small project doesn't need them). Note the two ORM lines: sqlalchemy is the ORM, flask-sqlalchemy is a thin integration that scopes a session to each web request. EF Core bundles both roles in one package.

Step 3 — the smallest possible Flask app

Flask's hello-world is famously five lines, and understanding them makes everything else legible:

from flask import Flask

app = Flask(__name__)          # the application object — like WebApplication in Program.cs

@app.route("/health")          # decorator = attribute routing: [HttpGet("/health")]
def health():                  # a "view function" — the action method
    return {"status": "ok"}    # returning a dict auto-serializes to JSON

This project does not put app = Flask(__name__) at module level, though. It wraps creation in a function — the application factory, covered in depth on the next page — so tests, dev, and prod can each build their own differently-configured instance. That decision was made on day one because retrofitting it later touches everything.

Step 4 — configuration and .env

Configuration is environment variables, loaded from a git-ignored .env file in dev (the committed .env.example documents every variable). The important ones:

FLASK_APP=app                # which package holds create_app() — used by the `flask` CLI
FLASK_CONFIG=development     # which config class to load (development/testing/production)
DATABASE_URL=postgresql+psycopg://erp:erp@db:5432/erp
SECRET_KEY=...               # signs the session cookie (like machine key / Data Protection)
The mapping: .env ≈ user-secrets + appsettings.Development.json; FLASK_CONFIG ≈ ASPNETCORE_ENVIRONMENT; the config classes in app/config.py ≈ the strongly-typed Options pattern. One nicety carried over from .NET habits: ProductionConfig.__init__ refuses to start without a real SECRET_KEY, the way a well-configured ASP.NET app fails fast on missing config.
DATABASE_URL's host is db when the app runs inside docker-compose (service names are DNS names on the compose network) but localhost when you run Flask directly on your machine against the container's published port. Half of all "cannot connect to database" moments in this stack are this line.

Step 5 — PostgreSQL via Docker Compose

No local database install. Dev runs Postgres in a container, declared once in docker-compose.yml:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: erp
      POSTGRES_PASSWORD: erp
      POSTGRES_DB: erp
    ports:
      - "5432:5432"        # published so host tools (psql, pytest) can reach it
    volumes:
      - pgdata:/var/lib/postgresql/data   # named volume = data survives restarts

docker compose up -d db      # start just the database, in the background
Equivalent to running SQL Server in a container instead of installing LocalDB — one command, disposable, identical on every developer's machine and in CI. The named volume is the part people miss: containers are throwaway, so the data directory is mounted from a Docker-managed volume that outlives them.

Step 6 — run it

flask run --debug            # ≈ dotnet run + hot reload + developer exception page

The flask CLI finds create_app() via FLASK_APP=app, builds the app, and serves it on http://localhost:5000 with auto-reload on file changes. In this project you normally don't even do that by hand — docker compose up starts db + app together, with the source bind-mounted into the container so edits reload live.

What existed at the end of phase 1

  • The folder layout from the overview page, with an app/ package and empty api/.
  • create_app() serving a static index.html, with JSON error handlers already in place.
  • Config classes for development / testing / production.
  • A Dockerized Postgres and a .env wiring the two together.
  • Agent tooling: scripts/t.py (test runner) and scripts/db.py (database lifecycle).
"I set up the error-handling contract and the config discipline before any feature code" is a strong architectural statement — it means every endpoint written later inherited a consistent JSON error envelope and fail-fast production config for free, instead of those being retrofitted.
