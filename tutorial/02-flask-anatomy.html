The major parts of a Flask project

The application factory, blueprints, the request lifecycle, and error handling — mapped onto Program.cs, controllers, and middleware.

The application factory: create_app()

Everything starts in app/__init__.py. Instead of a module-level global app, there is one function that builds and wires a fully-configured instance. Condensed from the real file:

def create_app(config_name=None):
    config_name = config_name or os.environ.get("FLASK_CONFIG", "development")
    config_class = config.get(config_name, DevelopmentConfig)

    # static_url_path="" serves app/static/ at the site root, so
    # app/static/parts.html is reachable at /parts.html
    app = Flask(__name__, static_folder="static", static_url_path="")
    app.config.from_object(config_class())

    db.init_app(app)              # bind the shared SQLAlchemy object to THIS app
    migrate.init_app(app, db)     # ...and Alembic

    register_error_handlers(app)  # every error becomes the same JSON envelope
    register_cli(app)             # the custom `flask seed` command

    @app.teardown_request
    def teardown_db_session(exception=None):
        ...                       # one transaction per request — see below

    from app.api.auth import bp as auth_bp
    from app.api.inventory import bp as inventory_bp
    # ... one import per module ...
    for bp in [auth_bp, inventory_bp, bom_bp, work_orders_bp,
               purchasing_bp, sales_orders_bp, dashboard_bp]:
        app.register_blueprint(bp)

    return app
This function is Program.cs. Line by line: config.from_object() ≈ loading appsettings.{env}.json; the init_app() calls ≈ builder.Services.AddDbContext(...); register_error_handlers ≈ app.UseExceptionHandler + ProblemDetails; the blueprint loop ≈ app.MapControllers(). The reason it's a function: pytest calls create_app("testing") to get an isolated instance per run, the same way your integration tests use WebApplicationFactory to spin up a configured TestServer.

Extensions and the circular-import trap

app/extensions.py is two lines: db = SQLAlchemy(...) and migrate = Migrate(), created unbound — not attached to any app yet. Models import db from there; the factory later binds it with db.init_app(app).

This is Flask's answer to a problem your DI container solves invisibly. In ASP.NET, DbContext is registered once and constructor-injected everywhere, so there is no import cycle. Python has no container: models need db, routes need models, the app needs routes — if the app also created db, you would have a circular import. Creating extensions unbound in a leaf module, then binding late, breaks the cycle. It is the one piece of Flask boilerplate with no .NET counterpart, and knowing why it exists is a good depth signal.

Blueprints: controllers by another name

A blueprint is a named group of routes defined away from the app and registered onto it. Each module in app/api/ declares one:

bp = Blueprint("inventory", __name__, url_prefix="/api")

@bp.get("/parts")
@require_login()
def list_parts():
    ...

@bp.post("/parts")
@require_login(role="admin")
def create_part():
    ...
Blueprint("inventory", __name__, url_prefix="/api") ≈ a controller class with [Route("api/[controller]")]. @bp.get("/parts") ≈ [HttpGet("parts")]. The route handler is a plain function returning a dict (auto-JSON), a (dict, status) tuple, or a Response — where you would return ActionResult<T>.

The request lifecycle, and one-transaction-per-request

Flask's pipeline: match URL → run before_request hooks → run the view function → run after_request → run teardown_request always, even when the view raised. This project uses teardown to enforce a rule from the architecture doc — every request is exactly one database transaction:

@app.teardown_request
def teardown_db_session(exception=None):
    if exception is None:
        try:
            db.session.commit()      # request succeeded -> commit its transaction
        except Exception:
            db.session.rollback()
            raise
    else:
        db.session.rollback()        # anything raised -> roll everything back
    db.session.remove()              # fresh session for the next request

Consequence: route code never calls commit. Handlers and services mutate objects and call db.session.flush() when they need generated IDs; the commit happens in exactly one place, on the way out. An exception anywhere in a request — even one an error handler converted into a clean 409 response — rolls back everything that request did.

This is the middleware-scoped-transaction pattern: like wrapping every request in a TransactionScope in a custom middleware, with SaveChanges forbidden in controllers. flush() ≈ SaveChanges() inside an open transaction (SQL sent, IDs populated, nothing durable yet); the teardown commit ≈ transaction.Commit(). More on this split on page 5.

flask.g — per-request state

g is a scratch namespace Flask resets on every request. The auth decorator stores the loaded user there (g.user), so any code deeper in the call stack can read who is acting without the user being passed through every function signature.

Direct equivalent: HttpContext.Items, or the ClaimsPrincipal on HttpContext.User for this specific use.

Decorators where .NET uses attributes: require_login

Authorization is a decorator in app/api/auth.py, used two ways: @require_login() (any authenticated user) and @require_login(role="admin"). Its skeleton:

def require_login(role=None):                  # runs once, at decoration time
    def decorator(view_func):                  # receives the route function
        @functools.wraps(view_func)            # keep the function's name/metadata
        def wrapper(*args, **kwargs):          # THIS runs on every request
            user = ...load from session cookie...
            if user is None:
                raise ApiError(401, "unauthenticated", ...)
            if role is not None and user.role != role:
                raise ApiError(403, "forbidden", ...)
            g.user = user                      # stash for the handler
            return view_func(*args, **kwargs)
        return wrapper
    return decorator
@require_login(role="admin") ≡ [Authorize(Roles = "admin")]. The mechanics differ: an attribute is declarative metadata that ASP.NET's filter pipeline reads; a decorator literally replaces the function with a wrapper at import time. That's why it is three nested functions — the outer call captures role, the middle receives the view function, the inner is what Flask actually invokes per request. functools.wraps matters: Flask names routes after the function, so without it every wrapped view would be named "wrapper" and the second registration would collide.

One JSON error envelope for everything

The architecture doc's rule: API consumers never receive HTML, and every error has the same shape:

{ "error": { "code": "insufficient_stock",
             "message": "Not enough stock to complete this work order.",
             "field_errors": { "sku": "SKU already exists." },
             "details": [ {"line": 2, "message": "..."} ] } }

Two mechanisms deliver it. Application code raises ApiError(status, code, message, ...) — a custom exception with a registered handler that serializes it. And for errors Flask raises on its own (404 route miss, 405 wrong verb, unhandled 500), register_error_handlers() maps each status to a default ApiError so even framework errors leave through the same door.

Identical intent to ProblemDetails + an exception filter: exceptions as control flow for error responses, one serializer, no HTML error pages leaking to an API caller. ApiError ≈ a custom exception + IExceptionFilter combo.

The flask CLI and custom commands

flask run, flask db upgrade (from Flask-Migrate), and this project's custom flask seed — registered in app/cli.py — all run inside an application context, meaning config and database are available exactly as in a request. flask seed is idempotent: it creates the demo users/parts/documents only if missing, so it is safe to run on every deploy.

≈ dotnet run -- seed with a custom IHostedService-style entry, or an EF HasData seeder — but as a first-class CLI verb.
If asked "what surprised you about Flask coming from ASP.NET?", a grounded answer from this project: how much ASP.NET gives you that Flask makes explicit — no DI container, no model binder, no [Authorize] — and that the explicitness cuts both ways: more boilerplate to write once (the factory, the decorator, the error handlers), but afterwards every behavior in the request path is code you can point at, not convention you have to know.
