PostgreSQL for the SQL Server developer

90% renames, 10% genuinely different — and the 10% shows up in this project's locking code.

Tooling: psql is your SSMS

The standard client is a REPL, not a GUI. In this project you reach it through the container:

docker compose exec db psql -U erp -d erp

erp=# \dt                  -- list tables            (≈ sys.tables)
erp=# \d parts             -- describe a table        (≈ sp_help 'parts')
erp=# \x                   -- toggle vertical output  (great for wide rows)
erp=# SELECT * FROM parts LIMIT 5;
erp=# \q                   -- quit

The backslash commands are psql metacommands, not SQL. GUIs exist (pgAdmin, DBeaver, DataGrip) but knowing the four above covers daily work.

Unquoted identifiers fold to lowercase in Postgres (SQL Server preserves case and is usually case-insensitive). Create a table as "StockMovements" and you must quote it that way forever. The ecosystem convention — followed by this schema — is snake_case everywhere: stock_movements, qty_on_hand. That's also why the Python models look like the SQL: the ORM never has to fight the naming.

The real difference: MVCC and locking

The biggest behavioral difference is concurrency. Postgres uses MVCC (multi-version concurrency control) natively: readers never block writers and writers never block readers — a SELECT sees a consistent snapshot without shared locks. SQL Server only behaves like this when READ_COMMITTED_SNAPSHOT is on; classic SQL Server readers take shared locks and get blocked.

When you genuinely need "read this row and keep others from changing it until I commit," you say so explicitly:

-- Postgres                                  -- SQL Server equivalent
SELECT * FROM parts                          SELECT * FROM parts
WHERE id = 42                                WITH (UPDLOCK, ROWLOCK)
FOR UPDATE;                                  WHERE id = 42;

This project's stock service does exactly this on every inventory change (via SQLAlchemy's with_for_update=True), because check-then-write on qty_on_hand is a race without it: two concurrent shipments could both read "5 on hand", both decide 3 is available, and drive stock negative.

And the follow-up you can volunteer: once multiple rows get locked per transaction (a work-order completion locks every BOM component and the product), two transactions locking the same rows in different orders can deadlock. The fix is the classic one — a global lock ordering. Every multi-part transaction in this codebase sorts part IDs ascending before locking. Same theory as SQL Server deadlock avoidance; Postgres just makes you ask for the locks explicitly instead of choosing hints.

Constraints instead of enums

Document statuses (draft / ordered / received...) are plain VARCHAR columns guarded by CHECK constraints, not Postgres's native ENUM type:

status VARCHAR(20) NOT NULL DEFAULT 'draft'
    CONSTRAINT ck_purchase_orders_status_valid
    CHECK (status IN ('draft', 'ordered', 'received', 'cancelled'))

Reason: adding a value to a CHECK constraint is a trivial migration; altering a native enum type is awkward. Same tradeoff discussion as .NET enums-as-int vs enums-as-string with a check constraint — this schema chose the readable, migration-friendly option.

Postgres administrivia this project actually uses

-- databases are cheap; dev and tests use two on one server
CREATE DATABASE erp_test;

-- drop even with clients connected (used by the demo-reset runbook)
DROP DATABASE erp WITH (FORCE);

-- test isolation: wipe all tables, reset identities, honor FKs — in one statement
TRUNCATE TABLE stock_movements, parts, users, ... RESTART IDENTITY CASCADE;
Postgres "database" ≈ SQL Server database; there is no instance-level master you manage much — but note you cannot DROP the database you're connected to, so maintenance commands connect to the built-in postgres database first (the master role in that one respect). TRUNCATE ... CASCADE has no SQL Server equivalent — there you'd delete in FK order or disable constraints; here one statement does it, which is why the test suite resets state this way between tests.

Drivers and connection strings

The app connects with psycopg 3 (the Microsoft.Data.SqlClient of Postgres). SQLAlchemy URLs name the dialect and driver in the scheme:

postgresql+psycopg://erp:erp@localhost:5432/erp
