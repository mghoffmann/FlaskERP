Defining data: SQLAlchemy models and Alembic migrations

EF Core code-first, translated. Same workflow, more explicit transaction control.

A model class, side by side with your mental EF entity

All 11 tables live in app/models.py. Here is the central one, Part, lightly trimmed:

class Part(TimestampedModel):                      # base adds id, created_at, updated_at
    __tablename__ = "parts"
    __table_args__ = (
        sa.CheckConstraint("part_type IN ('raw', 'finished')", name="part_type_valid"),
        sa.CheckConstraint("qty_on_hand >= 0", name="qty_on_hand_non_negative"),
    )

    sku:  Mapped[str] = mapped_column(sa.String(40), unique=True, nullable=False)
    name: Mapped[str] = mapped_column(sa.String(120), nullable=False)
    part_type: Mapped[str] = mapped_column(sa.String(20), nullable=False)
    unit: Mapped[str] = mapped_column(sa.String(20), nullable=False, server_default="ea")
    qty_on_hand: Mapped[Decimal] = mapped_column(
        sa.Numeric(12, 2), nullable=False, server_default="0"
    )
    reorder_point: Mapped[Decimal] = mapped_column(sa.Numeric(12, 2), nullable=False, server_default="0")
    unit_cost:     Mapped[Decimal] = mapped_column(sa.Numeric(10, 2), nullable=False, server_default="0")
    active: Mapped[bool] = mapped_column(sa.Boolean, nullable=False, server_default=sa.true())

    # navigation property: BOM lines where this part is the product
    bom_lines: Mapped[list["BomLine"]] = relationship(
        foreign_keys="BomLine.product_part_id", back_populates="product"
    )

One deliberate schema-design point: constraint names are generated from a naming_convention dict on the metadata — so every FK/CHECK/unique constraint has a predictable name, which matters the day a migration needs to drop one. EF names constraints predictably by default; SQLAlchemy makes you opt in, and this project did.

The session: a DbContext with the lid off

db.session is the unit-of-work object — it tracks loaded objects (identity map), collects your inserts/updates, and writes them when told. The verbs differ from EF in one important way:

EF CoreSQLAlchemyWhat it does
context.Parts.Find(42)db.session.get(Part, 42)PK lookup, identity-map first.
context.Parts.Where(p => p.Active).ToList()db.session.scalars(select(Part).where(Part.active)).all()Composable query. select() expressions ≈ LINQ expression trees.
context.Add(part)db.session.add(part)Start tracking a new object.
(automatic change tracking)(automatic change tracking)Mutate a loaded object's attribute; both notice by themselves.
SaveChanges()db.session.flush()Sends the SQL, populates generated IDs — but does not commit.
transaction.Commit()db.session.commit()Makes it durable. In this app, called only by the request-teardown hook.
The flush/commit split is the number-one EF-to-SQLAlchemy adjustment. EF's SaveChanges() commits immediately (unless you opened an explicit transaction); SQLAlchemy's session is always inside an open transaction, and flush() just pushes SQL into it. This project turns that into a rule: services and routes may flush() (e.g. to get a new work order's ID for its movement rows) but never commit() — the teardown hook owns the commit. One request, one transaction, enforced structurally.

Migrations: Add-Migration → flask db migrate

Alembic (wrapped by Flask-Migrate) is EF Migrations with the same three-beat workflow:

# 1. change the model classes in app/models.py, then autogenerate a migration:
flask db migrate -m "add reorder_point to parts"     # ≈ Add-Migration AddReorderPoint

# 2. REVIEW the generated file in migrations/versions/ — autogenerate is a draft,
#    not a decision. (Same discipline as reviewing an EF migration before committing.)

# 3. apply it:
flask db upgrade                                     # ≈ Update-Database

A generated migration is a Python file with upgrade()/downgrade() functions of imperative schema operations — the same shape as an EF migration's Up()/Down():

def upgrade():
    op.add_column("parts",
        sa.Column("reorder_point", sa.Numeric(12, 2),
                  server_default="0", nullable=False))

def downgrade():
    op.drop_column("parts", "reorder_point")

Three project-specific practices worth knowing:

  • migrations/env.py must import the models. Autogenerate works by diffing the live database against the model metadata; if nothing imports app/models.py, the metadata is empty and autogenerate cheerfully generates "drop every table". (EF avoids this because the DbContext names its sets.)
  • flask db check runs in CI. It fails the build if the models have drifted from the migration chain — i.e. someone edited a model and forgot to generate the migration. This is the guard EF users approximate with context.Database.GetPendingModelChanges()-style checks.
  • Production applies migrations at container start. The Docker entrypoint runs flask db upgrade before starting gunicorn, so a deploy and its schema change are one atomic event (≈ running Database.Migrate() at startup).

Seed data as a CLI command

flask seed (in app/cli.py) creates the demo world: two users (admin/operator), raw and finished parts, a BOM, and documents in every interesting state — including a work order that is deliberately short on components and an in-transit purchase order that resolves the shortage, so the demo has a story. It is idempotent (create-if-missing), safe to run repeatedly, and does all inventory changes through the stock service like any other caller.

≈ EF's HasData, but imperative and able to express "documents mid-lifecycle", which declarative seeding is bad at. The idempotency requirement is the same one you'd impose on a .NET seeder that runs on every deploy.
A crisp line for "how do you handle schema change?": "Models are the source of truth; Alembic autogenerates a draft migration that I review like any other code; CI refuses to merge if models and migrations disagree; and production applies pending migrations at startup, so a deploy can never run new code against an old schema." Every clause of that has an EF equivalent you already know — say both and you sound bilingual.
