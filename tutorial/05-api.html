Displaying and modifying data: the JSON API

Routes, hand-rolled validation, document state machines, and the one service that guards the business invariant.

Reading data: list and detail endpoints

Every module follows the same pattern. A list endpoint with query-string filters, and a detail endpoint by ID:

@bp.get("/parts")
@require_login()
def list_parts():
    query = select(Part)
    part_type = request.args.get("type")          # ?type=raw   (≈ [FromQuery])
    if part_type:
        query = query.where(Part.part_type == part_type)
    search = request.args.get("q")
    if search:
        query = query.where(or_(Part.sku.ilike(f"%{search}%"),
                                Part.name.ilike(f"%{search}%")))
    parts = db.session.scalars(query.order_by(Part.sku)).all()
    return {"parts": [part_to_dict(p) for p in parts]}
The visible difference from ASP.NET: no model binding and no automatic DTO serialization. request.args is the raw query string; the response is a dict you build via an explicit part_to_dict() mapper (the AutoMapper role, written by hand). One function per entity defines the wire shape — user_to_dict pointedly excludes password_hash, the same reason you use DTOs instead of returning EF entities. ilike is case-insensitive LIKE — needed because Postgres string comparison is case-sensitive, unlike typical SQL Server collations.

Writing data: validation by hand

Flask has no DataAnnotations. Input validation is explicit code, and the architecture doc fixes the error contract so every endpoint fails the same way:

@bp.post("/parts")
@require_login(role="admin")
def create_part():
    data = get_json_or_400()                      # 400 if body isn't valid JSON
    field_errors = {}
    sku = (data.get("sku") or "").strip()
    if not sku:
        field_errors["sku"] = "SKU is required."
    elif db.session.scalar(select(Part).where(Part.sku == sku)):
        field_errors["sku"] = "SKU already exists."
    if data.get("part_type") not in ("raw", "finished"):
        field_errors["part_type"] = "Must be 'raw' or 'finished'."
    if field_errors:
        raise ApiError(400, "validation_error", "Invalid part.", field_errors=field_errors)

    part = Part(sku=sku, ...)
    db.session.add(part)
    db.session.flush()                            # populate part.id — still uncommitted
    return part_to_dict(part), 201
field_errors ≈ ModelState; raise ApiError(...) ≈ returning ValidationProblem(ModelState). For documents with line items, errors use a details list of {line, field, message} — the same idea as ModelState keys like Lines[2].Qty, just as structured data. Libraries exist to get attribute-style validation in Python (pydantic, marshmallow); this project skipped them deliberately — at this size, explicit code is shorter than the abstraction and shows exactly what is checked.

Documents are state machines

Work orders, purchase orders, and sales orders each have a small fixed lifecycle, e.g. purchase orders: draft → ordered → received, with cancelled reachable before receipt. Mutations are action endpoints, not generic updates:

POST /api/purchase-orders/7/order       # draft   -> ordered
POST /api/purchase-orders/7/receive     # ordered -> received   (this one moves stock)
POST /api/work-orders/3/complete        # released -> done      (consumes + produces stock)

An action from the wrong state returns 409 with code invalid_transition — the transition table lives in one place per module and is tested exhaustively. This is why there is no PATCH /purchase-orders/7 {status: ...}: a status is a consequence of an action, never directly writable.

Same reasoning as exposing Approve() on a DDD aggregate instead of a settable Status property. If you've argued for that in .NET, this is that argument, shipped.

The stock service: one writer, explicit locks

The core business invariant: parts.qty_on_hand must always equal the sum of that part's rows in the append-only stock_movements ledger. The enforcement is architectural — exactly one function in the codebase may change stock, and every module calls it:

# app/services/stock.py — the ONLY writer of parts.qty_on_hand
def apply_movement(part_id, qty_delta, reason, user_id,
                   ref_type=None, ref_id=None, note=None):
    # SELECT ... FOR UPDATE — row-lock the part until this request's
    # transaction commits (≈ WITH (UPDLOCK) in T-SQL)
    part = db.session.get(Part, part_id, with_for_update=True)

    new_qty = part.qty_on_hand + qty_delta
    if new_qty < 0:
        raise InsufficientStockError(part, required=-qty_delta,
                                     on_hand=part.qty_on_hand)

    part.qty_on_hand = new_qty                      # the balance...
    db.session.add(StockMovement(                   # ...and its explanation,
        part_id=part_id, qty_delta=qty_delta,       #    in the same flush —
        reason=reason, user_id=user_id,             #    they can never diverge
        ref_type=ref_type, ref_id=ref_id, note=note))
    db.session.flush()                              # flush, never commit

Multi-part operations compose it. Completing a work order must consume every BOM component and produce the finished part, all-or-nothing:

# work-order completion, condensed:
lock_ids = sorted(component_part_ids + [product_part_id])   # global lock ORDER
for pid in lock_ids:
    db.session.get(Part, pid, with_for_update=True)          # lock ascending

shortfalls = [c for c in components if on_hand(c) < required(c)]
if shortfalls:
    raise ApiError(409, "insufficient_stock", ...,           # report ALL shortages,
                   details=[...one per short part...])       # not just the first

for c in components:
    apply_movement(c.part_id, -required(c), "wo_consume", g.user.id, "wo", wo.id)
apply_movement(product_part_id, wo.qty, "wo_produce", g.user.id, "wo", wo.id)
wo.status = "done"

Three things to be able to explain about this code:

  • Sorted locking prevents deadlocks. If completion locks parts {3,7} ascending while a shipment locks {7,3} in its own order, they can deadlock. Everything in this codebase locks part IDs ascending, so lock graphs can't cycle.
  • Verify-all-then-write. Shortfalls are checked for every component before any movement is written, so the 409 lists every missing part — one fix-and-retry round trip for the user, not N.
  • The ledger is auditable and reconcilable. stock_movements is append-only with a polymorphic reference (ref_type/ref_id → the WO/PO/SO that caused it); a reconciliation check (asserted in tests) proves qty_on_hand == SUM(qty_delta) at all times.
This page is the interview centerpiece. The one-sentence version: "Inventory is a denormalized balance plus an append-only ledger; one service function owns the pair, takes a row lock, and every business operation composes it inside the request's single transaction — so the balance and its history cannot diverge, concurrent writes cannot oversell, and multi-row operations lock in a global order so they cannot deadlock." Every clause maps to a line of code you can point at.

How a request flows, end to end

POST /api/work-orders/3/complete
  → require_login() wrapper: session cookie → load User → g.user   (401/403 exit here)
  → view function: validate state (409 invalid_transition exit)
  → lock parts ascending, verify all components (409 insufficient_stock exit)
  → apply_movement × N  (flushes, uncommitted)
  → return JSON 200
  → teardown_request: db.session.commit()          ← the ONLY commit
     (any exception above instead rolls back EVERYTHING — no partial completion)
