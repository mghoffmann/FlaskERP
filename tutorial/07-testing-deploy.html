Testing, Docker, and deployment

121 tests against a real Postgres, a dev/prod compose split, and CI that blocks broken deploys.

pytest, for the xUnit developer

xUnit / .NETpytest / this project
Test classes + [Fact]Plain functions named test_* in tests/test_*.py — no classes, no attributes.
[Theory] + [InlineData]@pytest.mark.parametrize — used here to sweep every endpoint for 401/403.
Constructor injection / IClassFixtureFixtures: a test asks for one by parameter name; pytest builds and injects it.

The whole suite hangs off tests/conftest.py (a discovery-based shared-fixture file — think "fixtures visible to every test in this folder, no import needed"):

# conftest.py, the load-bearing parts:

@pytest.fixture(scope="session")
def app():                                   # one app for the whole run
    app = create_app("testing")              # points at the erp_test database
    with app.app_context():
        db.drop_all(); db.create_all()       # fresh schema once per run
    yield app

@pytest.fixture(autouse=True)                # autouse = wraps EVERY test
def _isolated_db(app):
    yield                                    # test runs here...
    ...TRUNCATE all tables RESTART IDENTITY CASCADE...   # ...then full reset

@pytest.fixture
def admin_client(app, ...):                  # a logged-in test client
    client = app.test_client()
    client.post("/api/login", json={"username": "admin", "password": ...})
    return client                            # carries the session cookie afterwards

Two testing decisions worth defending out loud:

  • Real Postgres, not SQLite or mocks. The code under test leans on CHECK constraints, FOR UPDATE locking, and NUMERIC semantics — exactly the things a substitute database fakes differently. Same argument as refusing EF's InMemory provider for anything with transactions.
  • TRUNCATE between tests, not transaction-rollback isolation. The usual trick (run each test in a rolled-back transaction) is impossible here because the app genuinely commits — the teardown hook from page 2 is part of what's being tested. So each test runs against the real commit path, and the autouse fixture wipes all tables afterwards.

Coverage highlights across the 121: the parametrized auth sweep (every endpoint × anonymous and wrong-role, so forgetting a @require_login fails CI), state-machine transition tables, insufficient-stock with multi-part shortfall details, ledger reconciliation (qty_on_hand == SUM(qty_delta)), and seed idempotency.

Docker: dev and prod are the same stack, differently dressed

One Dockerfile builds the app image for both. The two compose files differ only in posture:

docker-compose.yml (dev)docker-compose.prod.yml
Servicesdb + appdb + app + caddy
App runssource bind-mounted, flask run --debug (live reload)the image as built, gunicorn with 2 workers — no debugger, no reload
Ports published5432 (for host psql/pytest) and 5000only 80/443 on Caddy — db and app are unreachable from outside
Data volumepgdatapgdata_prod (distinct name — can never collide with dev)

The image's entrypoint encodes the boot contract: wait for Postgres → flask db upgrade (apply pending migrations) → exec gunicorn. Every service has restart: unless-stopped, so a droplet reboot brings the whole stack back with no operator action.

gunicorn is the Kestrel of this stack: a production WSGI server running N worker processes (Python's GIL makes multi-process the scaling unit where .NET uses threads). Caddy plays the IIS/nginx reverse-proxy role with one superpower: given a real domain, it obtains and renews Let's Encrypt certificates automatically — the entire TLS story is two lines of Caddyfile.

CI/CD: GitHub Actions

.github/workflows/ci.yml runs on every push to main or development:

jobs:
  test:
    services:
      db: postgres:16 + healthcheck        # a real database next to the test VM
    steps:
      - checkout, set up Python 3.12, pip install
      - flask db upgrade                    # prove the migration chain applies cleanly
      - flask db check                      # prove models haven't drifted from migrations
      - pytest -q                           # the 121 tests

  deploy:
    needs: test                             # ← the gate
    if: push to main
    steps:
      - ssh into the droplet:  git pull --ff-only
                               docker compose -f docker-compose.prod.yml up -d --build

The deploy job is the CD half: a push to main reaches production only if the full suite passed, the droplet rebuilds the image and swaps only the app container (data and TLS certificates untouched), and the entrypoint applies any new migrations before serving. Day-to-day work happens on development; merging to main is the release action.

≈ Azure DevOps: build stage with a service container, then a release stage gated on it, deploying over SSH instead of an agent. needs: test is the stage dependency; the if: is the branch filter on the release trigger.

Production security posture (say it before they ask)

  • Database and app server publish no ports; only Caddy faces the internet, TLS-only.
  • Secrets live in a gitignored .env on the droplet; .env.example documents every variable; production refuses to boot on a missing SECRET_KEY.
  • Session cookies are HttpOnly + Secure; passwords hashed (werkzeug); login is timing-equalized so username existence can't be probed.
  • Containers run as a non-root user.
  • Known accepted gaps, on purpose and documented in the README: no CSRF tokens, no rate limiting, no backups — right-sized for a demo, and naming them is part of the demo.
Closing narrative, tying the whole walkthrough together: "Twelve requirement docs with acceptance criteria → a phased build along the dependency graph → every phase gated by tests that run against the real database → CI that refuses drift between models and migrations → CD that refuses to deploy a red build → a prod stack where the only thing reachable from the internet is the TLS proxy. Each piece is small, but they interlock — and I can walk you through any file in the repo and say why it's there." That last clause is what this tutorial was for.
