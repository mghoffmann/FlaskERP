Data preservation and error correction

Snapshots, point-in-time recovery, audit trails, undoing mistakes, and keeping it all off the server — the questions an in-house-ERP shop cares about most.

A small company running its own ERP has one asset that matters more than the code: the data. The questions that follow from that are: how do I freeze-frame the database and roll back to it? Who changed what, when, and why — and how do I undo it? And where do those safety copies live so that losing the server doesn't mean losing them? PostgreSQL has a ladder of answers, and this schema already has one built in.

Snapshots, tier 1: logical dumps with pg_dump

One command produces a consistent point-in-time copy of a database while it is live — MVCC gives the dump a stable snapshot without blocking writers:

# freeze-frame (custom format: compressed, selectively restorable)
docker compose -f docker-compose.prod.yml exec db pg_dump -U erp -Fc erp > erp-2026-08-21.dump

# roll back to it (--clean drops existing objects before recreating them)
docker compose -f docker-compose.prod.yml exec -T db pg_restore -U erp -d erp --clean < erp-2026-08-21.dump

This is the right tier for a small shop's nightly backup, and for the manual "snapshot before I run this risky migration" moment. Restore granularity is the whole dump: you get the database exactly as it was at dump time.

pg_dump ≈ BACKUP DATABASE to a .bak; pg_restore ≈ RESTORE DATABASE. The difference in flavor: a dump is logical (SQL statements / table data, portable across Postgres versions and even to other machines' architectures) where a .bak is a physical page copy. The physical analog exists too — pg_basebackup — and matters for the next tier.

Snapshots, tier 2: point-in-time recovery (PITR)

Postgres continuously writes every change to the WAL — the write-ahead log, the exact analog of SQL Server's transaction log — before touching the data files. If you (a) take a periodic physical base backup and (b) archive every WAL segment as it is produced, you can rebuild the database as of any instant: restore the base backup, set recovery_target_time = '2026-08-21 14:02:00', and Postgres replays the log up to one second before the bad delete, then stops.

Nobody wires this by hand in production. pgBackRest and wal-g are the standard tools: they manage base backups, ship WAL continuously to storage, enforce retention, and drive the restore. With WAL shipping, your recovery point is minutes, not last-night.

This whole tier is the full-plus-log-backup discipline you already know: base backup ≈ full backup, WAL archive ≈ log backups, recovery_target_time ≈ RESTORE ... WITH STOPAT. If you can explain SQL Server log-shipping, you can explain PITR — only the tool names change.

Snapshots, tier 3: machine images

SQL Server has a native CREATE DATABASE ... AS SNAPSHOT — an instant copy-on-write snapshot you can revert to. Postgres has no equivalent SQL object; the nearest things are filesystem-level (a ZFS or LVM snapshot of the data directory) or, for this deployment, a DigitalOcean droplet snapshot, which images the whole VM including the Docker volume that holds the data. Crude, but a fine belt-and-suspenders layer on top of dumps.

One more scope of "roll back" that costs nothing: inside a transaction, SAVEPOINT / ROLLBACK TO SAVEPOINT ≈ T-SQL's SAVE TRANSACTION. And this app gets request-scale rollback structurally — the one-transaction-per-request teardown from page 2 means any failed request undoes everything it did, automatically.

Who, what, when — the audit question

Three layers, from generic to the one this project ships:

Statement logging and pgAudit

Postgres can log every statement (log_statement = 'all', with log_line_prefix adding user, database, and timestamp). The pgAudit extension does it properly for compliance: structured audit records of who ran what, filterable by command type or table (≈ SQL Server Audit). This answers who/what/when — but it is a trail to read, not a mechanism to undo.

History tables — what you would add

SQL Server's best tool here is system-versioned temporal tables (FOR SYSTEM_TIME AS OF). Postgres has no built-in equivalent; the standard pattern is a generic trigger that writes each row's OLD/NEW images as JSONB into an append-only audit table. From that, "apply their opposite" is mechanical: restore the OLD image. If an interviewer asks what you'd add to make the ERP correction-proof, this is the answer — one generic trigger, applied to every table, about a day of work.

The WAL is not an undo log. SQL Server people sometimes reach for fn_dblog; the Postgres analogs (pg_waldump, logical decoding — the CDC hook that tools like Debezium use) let you inspect every change, but no relational database gives you "reverse transaction 4127." Undo is always either restore (PITR to just before) or compensate (apply the opposite operation). Design for the second and you rarely need the first.

The ledger this schema already has — lead with this

For the data that actually matters in an ERP — inventory — the schema is the audit log. stock_movements is append-only, and every row carries user_id (who), created_at (when), reason and ref_type/ref_id (why — which work order, purchase order, or sale), and qty_delta (what). Because apply_movement() is the only writer of stock, the correction mechanism falls out of the design: a mistake is undone by a compensating movement — a mistaken +50 receipt is corrected by posting a −50 adjustment with a note, through the same validated, locked, audited code path. History is never edited; the trail shows both the mistake and the fix, like a ledger in accounting.

"Nobody UPDATEs history in this schema. Inventory is a balance plus an append-only ledger; corrections are reversing entries posted by the same service that posted the original, so the audit trail is complete by construction — and a reconciliation test proves the balance equals the sum of the ledger at all times." That is architecture doing what most shops bolt on with tooling. Its honest limit: the ledger covers stock; auditing edits to names, prices, and document fields would need the trigger-based history layer above.

Decoupling backups from the database

The principle to state plainly: a backup on the same disk as the database is not a backup. The droplet dying, being compromised, or being fat-fingered takes both. The standard is 3-2-1 — three copies, two kinds of media, one off-site. The practical version for this deployment:

# nightly cron on the droplet: dump straight to S3-compatible object storage
# (DigitalOcean Spaces, ~$5/mo) without ever touching the local disk
docker compose -f docker-compose.prod.yml exec db pg_dump -U erp -Fc erp \
  | rclone rcat spaces:erp-backups/erp-$(date +\%F).dump
  • For PITR, pgBackRest and wal-g speak S3 natively — base backups and every WAL segment stream to the bucket continuously.
  • Harden the decoupling: give the droplet write-only credentials (it can add backups, never delete them — so a compromised server cannot destroy history), turn on bucket versioning or a retention lock, and prefer a different region than the droplet's.
  • Rotate: keep dailies for two weeks, weeklies for a few months — object storage lifecycle rules do this automatically.
A backup that has never been restored is a hope, not a backup. Schedule a periodic test restore into a scratch database (CREATE DATABASE erp_verify, restore, sanity-check row counts) — the failure mode this catches is the one where the cron job has been silently producing empty dumps for six months.

Closing honesty, which is itself a selling point: the demo's README documents "no backups" as an accepted scope cut — flask seed rebuilds the demo world in seconds, so backups would be theater for this deployment. Being able to say that, and then lay out this exact ladder — nightly dumps → WAL archiving → off-site object storage with write-only credentials → compensating-entry corrections — shows you distinguish between a demo's needs and a business's, which is precisely the judgment an in-house-ERP shop is hiring for.
