How Shopfloor ERP was built, from an empty folder

A walkthrough of the project for a developer fluent in SQL Server, .NET, Entity Framework, and Angular.

What the app is (the 30-second tour)

Shopfloor ERP is a small manufacturing ERP: a factory buys raw parts from suppliers (purchase orders), builds finished parts from them according to a bill of materials (work orders), and sells the finished parts to customers (sales orders). Every change to inventory — a receipt, a build, a shipment, a manual adjustment — is one row in an append-only stock_movements ledger, and a dashboard summarizes open documents and low-stock parts. The demo story a reviewer can click through: receive the in-transit purchase order → the blocked work order becomes completable → complete it → ship the sales order → watch the dashboard numbers move. That loop touches every module, which is why it exists.

The method: plan first, then build in phases

Before any code, a planning session produced the 12 documents in requirements/ — one architecture doc, one schema doc, one per feature module, plus testing and deployment. Each has explicit acceptance criteria. The build then followed the dependency order the docs themselves declare:

PhaseWhat gets builtPlanning doc
1. SkeletonProject layout, app factory, config, error envelope, Docker dev database00-architecture
2. SchemaAll 11 tables as SQLAlchemy models, the initial Alembic migration, flask seed01-database
3. AuthSession login, require_login decorator, admin/operator roles02-auth
4. Stock serviceapply_movement() — the single function allowed to change inventory03-inventory
5. ModulesInventory, BOM, work orders, purchasing, sales, dashboard — API + pages03–09
6. Tests + CI121 pytest tests against real Postgres; GitHub Actions10-testing
7. ProductionProd compose file, Caddy TLS, deploy runbook, CI-gated auto-deploy11-deployment
The strongest thing you can say about this project is not a Flask fact — it is the process: requirements with acceptance criteria came first, the build was phased along the dependency graph, every phase was gated by the test suite before its commits landed, and the commit history is granular enough to review each step in minutes. That is the same discipline as a .NET shop with a solution design doc and a CI-gated main branch — just executed with AI agents doing the typing and you directing and reviewing.

Rosetta stone: your stack → this stack

Almost everything in this project has a direct counterpart in the Microsoft ecosystem. Keep this table in your head and most of the codebase reads instantly:
